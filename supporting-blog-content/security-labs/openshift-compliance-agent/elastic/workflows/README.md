 # OpenShift compliance workflows for Elastic Stack

 This directory contains the four Elastic Workflows used by the OpenShift compliance agent to query cluster state and safely execute remediation tasks.

 All four workflows are provided in a single text file formatted as direct Kibana Dev Tools requests (`POST kbn:/api/workflows/workflow/`). You can copy and execute them directly in the Kibana Console without manually building the definitions in the UI.

 ---

 ## The four workflows

 The workflows provide deterministic, auditable actions between Elasticsearch and your OpenShift clusters:

 ### 1. `openshift-compliance-query-live-workload`
 - **Purpose:** Executes a read-only HTTP GET request against the OpenShift Kubernetes API.
 - **Use case:** When a compliance check fails, the agent uses this workflow to inspect pods, service accounts, and RBAC bindings to find the exact offending resource.
 - **Safety:** Read-only (`GET`). Never mutates live application workloads.

 ### 2. `openshift-compliance-read-live-state`
 - **Purpose:** Fetches the live custom resource definition (CRD) of a `ComplianceScan`, `ComplianceCheckResult`, or `ComplianceRemediation` directly from the `openshift-compliance` namespace.
 - **Use case:** Verifies the current cluster state before the agent recommends or executes an action.

 ### 3. `openshift-compliance-trigger-scan`
 - **Purpose:** Re-runs a specific compliance scan on a cluster by annotating the scan with `compliance.openshift.io/rescan: ""`.
 - **Use case:** Allows teams to re-evaluate compliance immediately after applying a fix without waiting for the scheduled scan interval.
 - **Safety:** Checks that the scan is currently in the `DONE` phase before annotating. If a scan is already running, the workflow exits safely.

 ### 4. `openshift-compliance-set-remediation-state`
 - **Purpose:** Applies (`apply: true`) or reverts (`apply: false`) an official `ComplianceRemediation` object generated by the Compliance Operator.
 - **Use case:** Remediates platform-level configuration issues using native Red Hat patches.
 - **Safety:** Performs a Kubernetes server-side dry run (`dryRun: true`) before applying the merge patch, confirming the patch succeeds before persisting changes.

 ## Prerequisites

 Before running these workflows, ensure the following are configured in your Elastic deployment:

 1. **Elastic Stack version:** 9.5 or later with an Enterprise license, or Elastic Cloud Serverless or Trial version.
 2. **Kubernetes connector:** Configure an Elastic Kubernetes connector for each monitored cluster.
    - **Important:** The connector name in Kibana must match the `cluster` name recorded in your compliance data (such as
 `ocp-na-prod`). The workflows use `{{ inputs.cluster }}` as the connector ID.
 3. **OpenShift service account permissions:** The service account configured on the connector requires:
    - Read permissions (`get`, `list`) on core resources (`pods`, `serviceaccounts`, `rolebindings`).
    - Patch and get permissions on `compliance.openshift.io` resources in the `openshift-compliance` namespace (`compliancescans` `complianceremediations`, `compliancecheckresults`).

 ## How to install via Kibana Dev Tools

 1. Open Kibana and navigate to **Management** > **Dev Tools** > **Console**.
 2. Open the text file containing the four workflow POST blocks.
 3. Copy and paste the entire contents into the Dev Tools Console editor.
 4. Run each `POST` request sequentially by clicking the green triangle play button next to each block.
 5. Verify the installation by listing your configured workflows:
GET kbn:/api/workflows or GET kbn:/api/workflows/workflow/<workflow-id>

 Once installed, these workflows appear in **Stack Management** > **Workflows** and can be attached directly to tools in **Elastic
 Agent Builder**.
